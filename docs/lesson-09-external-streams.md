# Lesson 9: External Streams & Iterators

## Learning Goals

After this lesson you should be able to:

- Explain why external streams are needed and what problem they solve
- Feed Java data into a Velox query plan using DownIterator and ExternalStream
- Use the BlockingQueue for async producer-consumer data feeding
- Understand the full data flow: Java data → DownIterator → ExternalStream → Velox scan operator
- Choose between DownIterator and BlockingQueue for your use case

---

## 9.1 The Problem: Getting Java Data into Velox

In Lesson 7, we learned that `TableScanNode` reads data via splits — typically from files (Parquet, ORC) through the Hive connector. But what if your data **doesn't come from files**?

Real-world scenarios:
- **Flink**: data arrives as a stream of row batches from upstream Flink operators
- **Custom sources**: data lives in a database, a message queue, or is generated by Java code
- **Pipeline chaining**: output of one Velox query feeds into another Velox query

In these cases, you need to **push data from Java into the Velox execution pipeline**. This is what external streams do.

---

## 9.2 The Big Picture

```
Java data source                    Velox execution pipeline
────────────────                    ────────────────────────

 Iterator<RowVector>                  TableScanNode
        │                                  │
        ▼                                  │ reads from
   DownIterator                            │
   (Java interface)                        ▼
        │                          ExternalStreamDataSource
        │  C++ calls back                  │
        │  into Java via JNI              │ calls read()
        ▼                                  ▼
   ExternalStream ◄────────────── ExternalStreamConnectorSplit
   (C++ object)                   (links split to stream by handle ID)
```

Or with the BlockingQueue variant:

```
Java producer thread               Velox execution pipeline
────────────────────                ────────────────────────

  queue.put(rowVector)              TableScanNode
        │                                  │
        ▼                                  ▼
   BlockingQueue  ◄──────────── ExternalStreamDataSource
   (C++ thread-safe queue)         (calls read() → blocks until data arrives)
        │
  queue.noMoreInput()
```

---

## 9.3 The Components

### UpIterator vs DownIterator

The project uses directional naming:

| Iterator | Direction | Purpose |
|----------|-----------|---------|
| **UpIterator** | C++ → Java | Pulls results **up** from Velox to Java (query output) |
| **DownIterator** | Java → C++ | Pushes data **down** from Java into Velox (query input) |

Both use the same three-state machine: `AVAILABLE`, `BLOCKED`, `FINISHED`.

### ExternalStream

A C++ interface that Velox's scan operator reads from:

```cpp
// ExternalStream.h
class ExternalStream {
    virtual std::optional<RowVectorPtr> read(ContinueFuture& future) = 0;
};
```

Two implementations:
1. **DownIterator** (C++) — wraps a Java `DownIterator` and calls back into Java via JNI
2. **BlockingQueue** — a C++ thread-safe queue that Java pushes data into

### ExternalStreamConnector

A custom Velox connector (registered as `"connector-external-stream"` during initialization) that reads from `ExternalStream` objects instead of files. It consists of:

- `ExternalStreamTableHandle` — identifies the table as an external stream source
- `ExternalStreamConnectorSplit` — carries the `ExternalStream`'s ObjectStore handle ID
- `ExternalStreamDataSource` — Velox's `DataSource` implementation that calls `ExternalStream::read()`
- `ExternalStreamConnector` — the connector factory

**Source:** `src/main/cpp/main/velox4j/connector/ExternalStream.h`

## 9.4 Method 1: DownIterator (Synchronous)

The simplest way to feed Java data into Velox. C++ calls back into Java to pull data synchronously.

### Step 1: Prepare your Java data as an Iterator

```java
List<RowVector> batches = ...;  // your data
Iterator<RowVector> javaIterator = batches.iterator();
```

### Step 2: Wrap it as a DownIterator

```java
DownIterator down = DownIterators.fromJavaIterator(javaIterator);
```

### Step 3: Bind it to an ExternalStream

```java
ExternalStream es = session.externalStreamOps().bind(down);
```

This sends the `DownIterator` to C++, which creates a C++ `DownIterator` object that holds a JNI reference to the Java `DownIterator`. When Velox calls `read()`, C++ calls back into Java's `advance()`/`get()`.

### Step 4: Build a plan that reads from it

```java
TableScanNode scanNode = new TableScanNode(
    "scan-1",
    schema,
    new ExternalStreamTableHandle("connector-external-stream"),
    List.of()   // no assignments needed for external streams
);

ConnectorSplit split = new ExternalStreamConnectorSplit(
    "connector-external-stream",
    es.id()     // the ExternalStream's ObjectStore handle
);
```

### Step 5: Execute and add the split

```java
Query query = new Query(scanNode, Config.empty(), ConnectorConfig.empty());
SerialTask task = session.queryOps().execute(query);
task.addSplit(scanNode.getId(), split);
task.noMoreSplits(scanNode.getId());
```

### Step 6: Read results

```java
Iterator<RowVector> results = UpIterators.asJavaIterator(task);
while (results.hasNext()) {
    RowVector batch = results.next();
    // process...
}
```

### Complete example

```java
// Chain two queries: output of query 1 → input of query 2
UpIterator query1Output = session.queryOps().execute(query1);
DownIterator down = DownIterators.fromJavaIterator(UpIterators.asJavaIterator(query1Output));
ExternalStream es = session.externalStreamOps().bind(down);

TableScanNode scan = new TableScanNode("scan-1", schema,
    new ExternalStreamTableHandle("connector-external-stream"), List.of());
ConnectorSplit split = new ExternalStreamConnectorSplit("connector-external-stream", es.id());

SerialTask task = session.queryOps().execute(new Query(scan, Config.empty(), ConnectorConfig.empty()));
task.addSplit(scan.getId(), split);
task.noMoreSplits(scan.getId());

// Iterate results from query 2
Iterator<RowVector> results = UpIterators.asJavaIterator(task);
```

**Source:** `src/main/java/org/boostscale/velox4j/iterator/DownIterators.java`, `QueryTest.testExternalStreamFromJavaIterator()`

### How the JNI callback works

When Velox needs data, the call chain is:

```
Velox scan operator
  → ExternalStreamDataSource::next()
    → ExternalStream::read()
      → C++ DownIterator::read()
        → JNI callback: Java DownIterator.advance()  ← crosses JNI
        → JNI callback: Java DownIterator.get()       ← crosses JNI
          → Java Iterator<RowVector>.next()
            → returns RowVector (C++ handle)
```

The C++ `DownIterator` suspends the Velox driver thread before calling into Java (via `SuspendedSection`), which allows other Velox operations (like spilling) to proceed if needed.

## 9.5 Method 2: BlockingQueue (Asynchronous)

For scenarios where the data producer and Velox consumer run on **different threads**, use a `BlockingQueue`.

### Step 1: Create a blocking queue

```java
ExternalStreams.BlockingQueue queue = session.externalStreamOps().newBlockingQueue();
```

The queue is both an `ExternalStream` (Velox reads from it) and a push API (Java writes to it).

### Step 2: Build and execute the plan (same as DownIterator)

```java
TableScanNode scanNode = new TableScanNode("scan-1", schema,
    new ExternalStreamTableHandle("connector-external-stream"), List.of());
ConnectorSplit split = new ExternalStreamConnectorSplit(
    "connector-external-stream", queue.id());

SerialTask task = session.queryOps().execute(
    new Query(scanNode, Config.empty(), ConnectorConfig.empty()));
task.addSplit(scanNode.getId(), split);
task.noMoreSplits(scanNode.getId());
```

### Step 3: Push data from a producer thread

```java
// Producer thread
queue.put(rowVector1);
queue.put(rowVector2);
queue.put(rowVector3);
queue.noMoreInput();   // signal end of data
```

### Step 4: Consume from a consumer thread

```java
// Consumer thread (can be the same or different)
Iterator<RowVector> results = UpIterators.asJavaIterator(task);
while (results.hasNext()) {
    RowVector batch = results.next();
    // process...
}
```

### The blocking behavior

The queue coordinates producer and consumer:

- **Consumer calls `task.advance()`** but queue is empty → returns `BLOCKED`
- **Consumer calls `task.waitFor()`** → blocks until data is available
- **Producer calls `queue.put(rv)`** → wakes up the consumer
- **Producer calls `queue.noMoreInput()`** → consumer eventually gets `FINISHED`

```
Timeline:

Consumer thread:     advance()→BLOCKED   waitFor()...........   advance()→AVAILABLE  get()→rv1
                                          (blocks)
Producer thread:                               queue.put(rv1)
                                               (wakes consumer)
```

### Two-thread example from tests

```java
// Consumer thread
Thread consumer = new Thread(() -> {
    while (true) {
        UpIterator.State state = task.advance();
        if (state == UpIterator.State.BLOCKED) {
            task.waitFor();     // blocks until producer pushes data
            continue;
        }
        if (state == UpIterator.State.FINISHED) {
            break;              // producer called noMoreInput()
        }
        RowVector batch = task.get();
        // process batch...
    }
});
consumer.start();

// Producer thread (main)
Thread.sleep(500);
queue.put(rowVector);
queue.noMoreInput();
consumer.join();
```

**Source:** `src/main/java/org/boostscale/velox4j/connector/ExternalStreams.java`, `QueryTest.testBlockingQueueNoMoreInputTwoThreads()`

## 9.6 BlockingQueue with InfiniteIterator

For long-running streaming scenarios where data arrives indefinitely, combine `BlockingQueue` with `InfiniteIterator`:

```java
ExternalStreams.BlockingQueue queue = session.externalStreamOps().newBlockingQueue();
// ... set up plan and task as before ...

InfiniteIterator<RowVector> out = UpIterators.asInfiniteIterator(task);

// Event loop
while (true) {
    if (out.available()) {
        RowVector batch = out.get();
        // process batch...
    } else {
        // No data right now. Could do other work, or block:
        out.waitFor();
        RowVector batch = out.get();
        // process batch...
    }
}
```

`InfiniteIterator` differs from the regular iterator:
- `available()` is **non-blocking** — returns `false` if no data yet (instead of blocking)
- `waitFor()` **blocks** until data arrives
- Never returns `FINISHED` — it expects the stream to continue indefinitely

**Source:** `src/main/java/org/boostscale/velox4j/iterator/UpIterators.java` (AsInfiniteIterator)

## 9.7 Applying Velox Operations to External Data

The real power of external streams is that you can apply **the full Velox query plan** to Java-provided data. The external stream is just a scan node — you can stack filters, projections, aggregations, joins on top:

```java
// Scan from external stream
TableScanNode scan = new TableScanNode("scan-1", schema,
    new ExternalStreamTableHandle("connector-external-stream"), List.of());

// Add a filter on top
FilterNode filter = new FilterNode("filter-1", List.of(scan),
    ConstantTypedExpr.create(new BooleanType(), new BooleanValue(false)));

// Execute the plan with the filter
Query query = new Query(filter, Config.empty(), ConnectorConfig.empty());
SerialTask task = session.queryOps().execute(query);
task.addSplit(scan.getId(), split);  // split points to the external stream
task.noMoreSplits(scan.getId());
```

This test (`QueryTest.testBlockingQueueWithInputFiltered()`) pushes data into a blocking queue, but the filter `false` discards all rows — the consumer sees `BLOCKED` forever because no output passes through.

## 9.8 DownIterator vs BlockingQueue: When to Use Which

| Criteria | DownIterator | BlockingQueue |
|----------|-------------|---------------|
| **Threading** | Single-threaded (C++ pulls from Java synchronously) | Multi-threaded (producer and consumer can be on different threads) |
| **Data availability** | Data must be ready when C++ calls `advance()` | Data can be pushed asynchronously at any time |
| **Backpressure** | Automatic — C++ only pulls when it needs data | Manual — producer must manage how fast it pushes |
| **Simplicity** | Simpler — wrap a `Java Iterator` | More complex — manage queue lifecycle and threading |
| **Use case** | Batch data that's already in memory | Streaming data from another thread (e.g., Flink operator) |
| **Termination** | `Iterator.hasNext()` returns false → FINISHED | Must call `queue.noMoreInput()` explicitly |

**Rule of thumb**: If your data comes from a Java `Iterator` or `List`, use `DownIterator`. If your data arrives asynchronously from another thread, use `BlockingQueue`.

## 9.9 The C++ ExternalStreamDataSource

For deeper understanding, here's how the C++ side reads from an external stream:

```cpp
// ExternalStream.cc — ExternalStreamDataSource::next()
std::optional<RowVectorPtr> ExternalStreamDataSource::next(uint64_t size, ContinueFuture& future) {
    while (true) {
        if (current_ == nullptr) {
            if (streams_.empty()) return nullptr;  // all streams exhausted
            current_ = streams_.front();
            streams_.pop();
            continue;
        }
        // Suspend the Velox driver before calling external (Java) code
        SuspendedSection ss(driverThreadCtx->driverCtx()->driver);
        const std::optional<RowVectorPtr> vector = current_->read(future);
        if (vector == nullptr) {
            current_ = nullptr;  // end of current stream, try next
            continue;
        }
        return vector;  // data available
    }
}
```

Key details:
- **`SuspendedSection`**: Before calling `read()` (which may call into Java via JNI), the Velox driver is suspended. This tells Velox "I'm waiting on external I/O" so it can perform memory reclamation or spilling on other drivers if needed.
- **Multiple streams**: `ExternalStreamDataSource` supports a queue of streams (from multiple splits). Each split adds one `ExternalStream` to the queue.

## 9.10 Key Takeaways

1. **External streams solve the "Java data → Velox" problem**. They let you feed data from Java code into a Velox query plan, enabling use cases beyond file scanning.

2. **Two methods**: `DownIterator` for synchronous single-threaded feeding (simpler), `BlockingQueue` for async multi-threaded feeding (more flexible).

3. **Reuses the connector/split pattern**. External streams plug into Velox via `ExternalStreamTableHandle` + `ExternalStreamConnectorSplit`, so the rest of the plan (filter, project, join, etc.) works unchanged.

4. **The split carries the stream's handle ID**. `ExternalStreamConnectorSplit` contains the `ExternalStream`'s ObjectStore handle, which the C++ `DataSource` uses to look up the actual stream object.

5. **`SuspendedSection` for safety**. Before calling into Java, the Velox driver is suspended to allow memory reclamation and avoid deadlocks.

6. **`queue.noMoreInput()` is mandatory** for BlockingQueue. Without it, the consumer blocks forever waiting for more data.
